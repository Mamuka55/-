## 2. Ключевые решения

### 2.1. Backend — Node.js + TypeScript + Fastify

В ТЗ стек backend не зафиксирован. Выбран Node/TS, потому что:

- **один язык** на Electron main, preload, renderer и backend — меньше контекстных
  переключений у одного разработчика;
- **общий модуль токенов**: `shared/tokens.js` (цвета, роли, статусы, категории ошибок)
  импортируют и backend, и Electron, и renderer. Расхождение «цвета в БД vs цвета в UI»
  исключено конструктивно;
- Fastify даёт валидацию, хуки и низкие накладные расходы без тяжёлой DI-машины
  (в отличие от NestJS) — проект небольшой, а перенос на VPS должен быть простым;
- TypeScript критичен именно здесь: RBAC, версионирование и diff — это много
  мелких структур, где ошибка типа стоит дорого.

### 2.2. Один слой доступа к БД вместо ORM

`backend/src/db/index.ts` — тонкая обёртка с тремя реализациями:

| Драйвер | Когда | Примечание |
|---|---|---|
| `better-sqlite3` | локальная разработка (по умолчанию) | нативный, быстрый, WAL |
| `sql.js` (WASM) | fallback без нативных зависимостей | включается автоматически, если `better-sqlite3` не собрался; держит БД в памяти и пишет файл с debounced flush |
| `pg` (PostgreSQL) | production на VPS (§64) | |

Почему не Prisma/TypeORM:

- миграции нужны **простые и переносимые**: SQL-файлы с плейсхолдерами `{PK}`,
  `{TIMESTAMP}`, `{NOW}` подставляются по драйверу. Один набор миграций работает
  и на SQLite, и на PostgreSQL;
- в SQL запросах всегда пишется `?`, для PostgreSQL он транслируется в `$1..$n`
  (`toDriverSql`) с корректной обработкой строковых литералов и комментариев;
- нет скрытых N+1 и «магии» при вычислении эффективных permissions —
  этот запрос слишком важен, чтобы его генерировал ORM.

**Ограничение `sql.js`:** база целиком живёт в памяти процесса, поэтому два
одновременно запущенных backend'а затрут данные друг друга. От этого защищает
`backend/src/config/lock.ts` — второй экземпляр не стартует и печатает pid/port
уже работающего. На `better-sqlite3` и PostgreSQL такого ограничения нет.

### 2.3. Собственный BM25-поиск вместо FTS5/tsvector

Это одно из самых важных решений. Причины:

1. **Русская морфология.** FTS5 не умеет стемминг для ru: «зелёных» не нашло бы
   «зеленые». В PostgreSQL `'russian'`-конфигурация есть, но тогда поведение
   поиска отличалось бы между локальной разработкой и production — а для
   RAG это критично (ответы на dev и на VPS должны совпадать).
2. **Переносимость.** `sql.js` собран без FTS5 (`CREATE VIRTUAL TABLE … fts5`
   → `no such module: fts5`). Ставить поиск в зависимость от драйвера нельзя.
3. **Жёсткое разделение баз (§59).** Индекс физически разделён по `doc_type`,
   поэтому запрос в режиме ПРАВИЛА **не может** вернуть документ LAW —
   это не фильтр поверх выдачи, а свойство самого индекса.

Устройство индекса:

```
search_terms(term, doc_type, field, postings JSON [[chunkId, tf], …], df)
chunk_terms(chunk_id, field, term)      -- обратный список для переиндексации
```

- токенизация: слова и числа + **основа** слова (упрощённый алгоритм Соболева:
  отсекаются возвратные, прилагательные и существительные окончания, производные суффиксы);
- стоп-слова отбрасываются, **но токены с цифрами сохраняются всегда** — иначе
  запрос «статья 12.4» потерял бы номер;
- ранжирование: два прохода. Первый — грубая оценка `idf · tf` для отбора кандидатов,
  второй — нормировка по длине chunk'а (`k1=1.4`, `b=0.72`);
- диверсификация: не более 2 фрагментов одного документа в выдаче, иначе один
  длинный Penal Code вытеснил бы все остальные источники;
- если chunk-поиск пуст, дополнительно ищем по заголовкам документов
  (`searchDocuments`) — чтобы честно сказать «такой закон есть, но по вашему
  вопросу в нём ничего не найдено».

Индекс пересобирается при каждой новой версии документа и доступен для полной
переиндексации: `npm run kb:reindex`.

### 2.4. AI-провайдер как абстракция

`backend/src/ai/providers/index.ts` описывает интерфейс `LLMProvider` с четырьмя
реализациями:

| Провайдер | Что это | Когда использовать |
|---|---|---|
| `groq` | бесплатный API, OpenAI-совместимый, `llama-3.3-70b-versatile` | **по умолчанию**: быстрый и бесплатный |
| `openai_compatible` | любой OpenAI-совместимый endpoint (OpenRouter, vLLM, LM Studio) | если нужен другой каталог моделей |
| `ollama` | полностью локально, без ключей и интернета | если тексты правил не должны покидать сервер |
| `mock` | детерминированная заглушка | разработка UI, тесты, офлайн |

Смена провайдера — одна строка `AI_PROVIDER` в `.env`. RAG-конвейер от провайдера
не зависит. Embeddings вынесены в опциональный метод `embed()`: по умолчанию поиск
полностью лексический, семантическое переранжирование можно включить позже
(`EMBEDDING_ENABLED=true`) без изменения схемы — колонка `document_chunks.embedding`
уже есть, для PostgreSQL в миграции заготовлен закомментированный `pgvector`.

### 2.5. Почему модель не вызывается при пустой выдаче

`ai/rag/pipeline.ts`: если `retrieve()` не нашёл ни одного фрагмента, конвейер
**не обращается к LLM вообще** и сразу возвращает формулировку из ТЗ §14:

> В официальной базе EpicRP не найдено подтверждённой информации для однозначного ответа.

Это даёт три эффекта:

- галлюцинация на пустом контексте невозможна конструктивно, а не «потому что промпт строгий»;
- экономия токенов и latency;
- в `ai_requests.status` остаётся `no_data` — администратор в отчёте видит,
  что проблема в поиске/базе, а не в модели (§18: «Ошибка поиска» / «Устарела база»).

### 2.6. Источники формирует retrieval, а не модель

Все поля карточки источника (название документа, категория, раздел, пункт,
дата редакции, версия, URL, id темы и поста) собираются в `ai/rag/retrieval.ts`
из базы. Модель получает их как пронумерованный список и возвращает
`source_indexes` — индексы использованных источников. Индексы вне диапазона
**отбрасываются** (`pipeline.ts` → `parseAnswer`), поэтому «вымышленный источник»
не может попасть в окно источников даже при сбое модели (§12, §14).

Ответ модели требуется в виде JSON (`response_format: json_object` где поддерживается),
но парсер терпим: `extractJson()` снимает markdown-обёртку и находит первый
сбалансированный объект. Если модель ответила прозой — пользователь увидит её текст,
а вердикт станет `unknown`, но интерфейс не упадёт.

### 2.7. Окно источников — отдельный BrowserWindow (§10, §11)

Не панель внутри основного окна, а именно отдельное окно: панель остаётся
56-пиксельной полосой поверх игры, а карточки источников читаются в вертикальном
окне справа. Геометрия считается в `windows.js#positionSourcesWindow()`:
привязка к правому краю панели с выравниванием по её нижнему краю; если справа
не хватает места — окно переносится влево от панели; координаты всегда
зажимаются в `workArea` активного дисплея.

### 2.8. Настройки — внутри панели, не отдельным окном (§19)

Основное окно **растёт вниз** (`setPanelHeight`) и показывает либо ответ, либо
настройки — никогда оба сразу. Высоту сообщает renderer через
`epic:panel:resize`, а main process пересчитывает позицию так, чтобы нижний край
панели оставался на месте (панель обычно у нижнего края экрана).

### 2.9. Окно базы знаний — обновления и история ВНЕ настроек (§23–§26)

Кнопка «Посмотреть» в разделе «Правила» открывает выпадающую область панели
`pane-kb` (IPC `epic:kb:open` → `main:open-kb`) с двумя вкладками:
«Обновления» (две колонки: список изменений за день слева, «Было / Стало»
с word-level diff справа) и «История изменений» (дни с итогами, клик по дню
открывает его обновления). Кнопка «История изменений» из самой вкладки
«Правила» убрана по требованию пользователя — история доступна переключателем
внутри области БЗ. История ответов ИИ — отдельное окно `history.html` СЛЕВА
от панели (окно источников — справа; `windows.js#createHistoryWindow`,
IPC `epic:history:open` / `epic:history:pick`). Внутри панели настроек эти
экраны не рисуются: настройки остаются компактным дропдауном панели (§19).
Вся отрисовка вынесена в `renderer/scripts/kbview.js` — её же использует демо.

Отдельные окна (не вкладки и не inline-модалки):
- `confirm.html` — подтверждение «Спросить ИИ?» перед отправкой вопроса
  (остаток дневного лимита + прогресс-бар; IPC `epic:ask:confirm` →
  `epic:ask:confirm:result`, main process держит promise панели);
- профиль и аккаунт (аватар, роль, «@ник · вход через Telegram», карточка
  «Ответы ИИ сегодня», «Выйти из аккаунта») — НЕ отдельное окно: вкладка
  «Профиль» в настройках панели (`profileview.js`), открывается кликом по
  пилюле пользователя. Отдельное окно `profile.html` удалено по требованию
  пользователя.

Положения окон истории/источников запоминаются В ПРЕДЕЛАХ СЕАНСА
(`windows.js#memBounds`): пересозданное окно возвращается туда, куда его
перетащил пользователь; дефолтные позиции вычисляются только если окно
в этом сеансе не двигали. Положение ПАНЕЛИ переживает перезапуск:
`panelX/panelY` в `settings.json` пишутся и из renderer (`epic:panel:move`),
и из main по событию `moved` (нативный drag за `app-region: drag` зоны);
значения локальные для устройства и не синхронизируются с сервером.

### 2.10. Автоскрытие при клике вне окна (§29)

Механизм — событие `blur` основной панели: любой клик по игре, рабочему столу
или чужому приложению забирает фокус, и через 120 мс оверлей прячется в трей.
Чтобы blur reliably возникал, `showOverlay()` передаёт панели фокус
(`main.focus()`), а перед скрытием проверяется:

1. `hideOnOutsideClick` из настроек;
2. `alwaysOnTop`: ЗАКРЕПЛЁННОЕ звёздочкой окно при клике вне НЕ прячется
   (требование пользователя) — автоскрытие работает только у откреплённого окна;
3. не ушёл ли фокус на наше же окно: `BrowserWindow.getFocusedWindow()`
   сверяется со списком `ownWindows()` (панель, источники, история,
   подтверждение, профиль, админ, auth, blocked) — клик по ним оверлей не прячет.

Сочетания Ctrl+H (история) / Ctrl+O (источники) / Ctrl+P (закрепить)
зарегистрированы В MAIN PROCESS через `globalShortcut`
(`ipc.js#registerComboShortcuts`) и работают глобально — даже когда фокус
в игре, а не на панели; значения меняются перехватом в разделе «Клавиши»
и перерегистрируются при каждом изменении настроек.

Ранее здесь использовалось событие `screen.on('screen-spy-captured')`, которого
в Electron **не существует**: слушатели только накапливались (утечка
MaxListenersExceededWarning), а скрытие всё равно делал blur. Механизм удалён.

Приложение при скрытии **не завершается**: окна прячутся, процесс и трей остаются (§27).

### 2.11. Единая учётная запись и роли (§34–§46)

```
users ──< identities (provider + provider_user_id, UNIQUE)
  │
  └─< user_roles >── roles (level 1..8, is_system)
  │                     └─< role_permissions >── permissions
  └─< user_permission_overrides (effect: allow | deny)
```

- Discord и Telegram — **внешние identity provider'ы**: они дают `id`, `username`,
  `display name`, `avatar` (§35, §36), но **не определяют роль**;
- уникальность `(provider, provider_user_id)` гарантирует, что одна внешняя
  идентичность принадлежит ровно одному Epic AI Account (§37);
- второй провайдер привязывается к существующему аккаунту: если пользователь уже
  авторизован, callback не создаёт новый аккаунт, а вызывает `linkIdentity()`;
- эффективные права: `permissions ролей ∪ allow-overrides − deny-overrides`,
  то есть **deny всегда приоритетнее** (§44);
- иерархия назначения (§46): `targetLevel < actor.maxLevel`, системные роли
  (`is_system=1`, то есть Developer) не назначаются через панель вовсе;
- блокировка (§41): `users.status='blocked'` → все сессии помечаются
  `revoked_at/revoke_reason='blocked'`, а `authenticate()` при попытке входа
  с отозванным по блокировке токеном возвращает контекст со `status='blocked'`,
  чтобы клиент получил **403 «Аккаунт заблокирован»**, а не безликое 401.

### 2.12. Bootstrap первого Developer (§45)

Developer не создаётся и не выдаётся административной панелью. Есть ровно два пути:

- CLI: `npm run bootstrap:developer -- --discord <id> | --telegram <id>`;
- HTTP: `POST /api/bootstrap/developer` с `BOOTSTRAP_TOKEN`.

Оба одноразовые: как только в системе появляется хоть один Developer,
эндпоинт навсегда возвращает `409 already_bootstrapped` — **проверка количества
разработчиков выполняется до проверки токена**, чтобы endpoint нельзя было
использовать для перебора. Действие пишется в Audit Log.

### 2.13. Version Manager и diff (§53–§55, §24)

Приём документа (`knowledge/ingest.ts`) — единственный путь в базу, им пользуются
и crawler, и ручной импорт:

```
нормализация текста → sha256(normalized) → сравнение с documents.content_hash
  ├── хэш совпал      → UNCHANGED (обновляются только метаданные)
  ├── документа нет   → NEW, version 1
  └── хэш изменился   → UPDATED, version N+1 + word-level diff
```

- старая версия **не удаляется**: `document_versions` хранит полный текст каждой редакции;
- нормализация перед хэшем (`normalizeForHash`) убирает незначащие различия
  пробелов и переносов — иначе хэш «дрожал» бы от невидимых правок вёрстки;
- diff считается **на уровне слов** (§24), а не абзацев: токенизация сохраняет
  пробелы и пунктуацию, LCS с предварительным срезом общих префикса/суффикса,
  для больших фрагментов — поблочное сравнение по абзацам с рекурсивным word-diff
  внутри пары. Результат (`ops: [{kind: equal|del|ins, text}]`) сохраняется
  в `document_versions.diff_from_prev` и в `document_changes.diff_json`,
  поэтому экран «Обновления за сегодня» не пересчитывает diff на лету;
- лента изменений материализована в `document_changes` (по дням) — иначе каждый
  запрос «что изменилось сегодня» сканировал бы все версии.

### 2.14. Chunking под цитирование

`knowledge/text.ts` режет документ так, чтобы пункт правила по возможности
попадал в chunk целиком — иначе AI цитировал бы половину нормы:

1. `htmlToText()` — XenForo `bbWrapper` → текст с сохранением структуры строк.
   Удаляются zero-width-символы, которые XenForo вставляет после заголовков
   (`&#8203;` и литеральный U+200B) — без этого хэш и diff «дрожали» бы;
2. `reflowLongLines()` — **обязателен**: реальные документы на форуме вставлены
   одной строкой (Penal Code — 86 730 символов без единого переноса). Длинные
   строки режутся по границам предложений и по маркерам «Статья/Глава/§/4.2»;
3. `joinStandaloneMarkers()` — XenForo часто оформляет номер раздела отдельной
   цветной строкой («1.»), а заголовок идёт следующим абзацем; склеиваем их;
4. атомы режутся по пустым строкам, нумерованным пунктам и заголовкам, затем
   склеиваются до `RAG_CHUNK_CHARS` (1200) с перекрытием 180 символов;
5. `heading` chunk'а — это «Пункт 4.2» / «Статья 12.4» / «ГЛАВА 1. …», который
   показывается в окне источников (§11).

Проверено на живом форуме: тема «Правила сервера» (id 13) → 2 718 символов → 3 chunks;
«Конституция штата Сан-Андреас» (id 68) → 17 087 символов → 18 chunks;
«The Penal Code» (id 191, 22 поста, 2 страницы) → 105 chunks, 31 уникальный заголовок.

> Важно: **документ = тема целиком, а не первый пост.** Первый пост Penal Code
> содержит только заголовок (32 символа), а главы разнесены по 22 постам.
> Поэтому `postsPerDocument` по умолчанию — все посты темы, а посты сортируются
> по `postId` (страницы темы склеиваются в порядке обхода, а не в порядке документа).

### 2.15. Crawler: три шага и строгая вежливость

```
discoverNodes()      GET /                     → 62 раздела, дерево с parent/child
discoverThreads()    GET /forums/<slug>.<id>/  → темы раздела (+ page-N по <link rel="next">)
fetchThread()        GET /threads/<slug>.<id>/ → посты: article.message-body .bbWrapper
fetchRss()           GET /forums/<…>/index.rss → дополнительный сигнал о новом (§57)
```

Проверено на живом форуме 06.10.2026: главная страница → 62 узла, из них
19 классифицированы как RULE/LAW, включая корректное определение архивов
(`arkhiv.115/120/121/122/123` → `isArchive=true`).

Классификация разделов (`crawler/index.ts#classifyNodes`) работает в два прохода:
сначала по заголовку и явно заданным node id из `.env`, затем — наследованием
от родителя. Без второго прохода терялось бы дерево «Правила сервера» (узел 30 —
категория, её дети 38–41 — форумы). Разделы-не-документы отсекаются
`IGNORE_HINTS`: биографии, предложения, жалобы, мероприятия, вакансии, отчёты.

Отдельно: **жалобы** формально лежат внутри «Министерства Юстиции», но это
обращения граждан, а не нормы права — они исключены из базы.

Все сетевые детали и правовые ограничения — в [`LEGAL.md`](LEGAL.md).

### 2.16. Синхронизация (§56)

- планировщик (`http/scheduler.ts`) читает интервал **из базы**
  (`app_settings['sync.interval_minutes']`), поэтому частота меняется из админки
  без перезапуска — это и есть «позже частота может быть вынесена в серверную настройку»;
- при `CRAWLER_ENABLED=false` планировщик не делает ничего;
- быстрый путь без сети: если `documents.source_modified_at` совпал с `lastPostAt`
  темы из списка, страница темы не загружается вовсе. Повторный прогон по разделу
  «Общие правила» дал `0 новых, 0 изменено, 5 без изменений` при 7 загруженных страницах;
- глобальный флаг `running` не даёт двум синхронизациям идти одновременно
  (`409 sync_in_progress`);
- каждая синхронизация пишется в `sync_logs` (счётчики NEW/UPDATED/ARCHIVED/UNCHANGED,
  число страниц, ошибка, предупреждения), каждое изменение документа — в
  `document_changes`; событие попадает в Audit Log.

## 4. Безопасность (§62)

| Угроза | Мера |
|---|---|
| Утечка секретов в клиент | Electron знает **только** `backendUrl`. `AI_API_KEY`, `DISCORD_CLIENT_SECRET`, `TELEGRAM_BOT_TOKEN`, `DB_PASSWORD` читаются лишь `backend/src/config/index.ts` из `backend/.env` и никогда не сериализуются в ответы API |
| XSS в renderer | `contextIsolation: true`, `nodeIntegration: false`, строгий CSP в каждом HTML (`default-src 'none'`), никаких `innerHTML` с пользовательскими данными — только `textContent`/`createTextNode` |
| Произвольный IPC | `preload/index.js` пропускает вызовы только по белому списку каналов (`INVOKE`/`RECEIVE`); всё остальное отклоняется |
| CSRF при cookie-авторизации | Глобальный хук: любой не-GET запрос к `/api/*` обязан нести `X-Epic-Client: desktop \| admin-web \| cli`. Чужой сайт такой заголовок поставить не может |
| Кража сессии | В БД хранится только `sha256(token)`, токен — 48 байт `randomBytes`, `httpOnly`, `secure` в production, TTL 30 дней |
| Подмена auth-ответа Telegram | Проверка подписи по алгоритму Telegram (`HMAC_SHA256(data_check_string, SHA256(bot_token))`) + проверка возраста `auth_date` |
| OAuth CSRF | `state` с временем жизни 10 минут и одноразовым потреблением |
| Доступ заблокированного | Проверка `status='blocked'` **на backend при каждом запросе** + инвалидация всех сессий (§41) |
| Подделка источника AI | `source_indexes` фильтруются по фактически найденным; пустая выдача → LLM не вызывается |
| Изменение Audit Log | Для `/api/audit-logs` зарегистрированы только GET; POST/PUT/PATCH/DELETE возвращают `405 audit_readonly` (§50) |

## 5. Перенос local → VPS (§63 → §64)

Изменения на стороне клиента — **одно поле конфига**. Всё остальное уже готово:

| Что | Локально | На VPS |
|---|---|---|
| Backend | `embeddedBackend: true` — Electron сам поднимает `npx tsx src/index.ts` | `embeddedBackend: false`, `backendUrl: https://api.…` |
| БД | `DB_DRIVER=sqlite` | `DB_DRIVER=postgres` |
| Секреты | `backend/.env` | `backend/.env` или переменные окружения systemd/Docker |
| TLS | не нужен | reverse proxy (nginx/Caddy), `trustProxy: true` уже включён |
| Cookie | `secure: false` | `secure: true` автоматически при `NODE_ENV=production` |
| Crawler | на ПК разработчика | на VPS, рядом с БД |

Миграции и сиды применяются автоматически при старте backend'а (`src/index.ts`),
поэтому развёртывание — это `git pull && npm ci && npm run build && systemctl restart`.

## 6. Что намеренно НЕ сделано на первом этапе

| Отложено | Почему |
|---|---|
| Semantic search / embeddings | Лексический BM25 со стеммером уже даёт релевантную выдачу на корпусах такого размера. Колонка `embedding` и заготовка `pgvector` в миграции есть — включается без изменения схемы |
| UI-фреймворк | ТЗ §2 прямо говорит «без обязательного тяжёлого UI-фреймворка на первом этапе» |
| Streaming ответов | Панель 56 px и окно источников не подразумевают «печатающегося» текста; ответ приходит одним блоком за ~1–2 с |
| Автоматическая классификация ошибок AI (§18) | Реализована **предварительная подсказка** (`suggestAnalysis`: `no_data → search_miss`, `error → technical`, `outdated → kb_outdated`), итоговое решение принимает администратор. Полная автоматика имеет смысл после накопления статистики |
| Мобильный/web-клиент | Не требуется ТЗ |
